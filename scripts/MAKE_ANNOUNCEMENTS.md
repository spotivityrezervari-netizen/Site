# Manual announcements in Make

`make-announcements.mjs` builds two local blueprints: `clients` and `admins`. It makes no network requests, creates no credentials, runs no scenario, and sends no email. Audience is literal in every RPC and cannot be changed in the first module. Existing notifications are separate.

Provide the Supabase HTTPS origin, its **public anonymous key**, and numeric Make API-key keychain IDs. The keychain must inject `x-spotivity-announcement-key`; its dedicated random token is stored only by Make, with a hash in the private database credential table. Never copy an environment proxy credential into a blueprint or configuration file. Gmail uses existing connection `11897572` unless explicitly overridden.

Import `buildAnnouncementScenario` for each audience, or run `node scripts/make-announcements.mjs PUBLIC_CONFIG.json OUTPUT_DIRECTORY`. Configuration shape is `{supabaseUrl,anonKey,keychainIds:{clients,admins},gmailConnectionId,teamId}`. Outputs contain public configuration and credential IDs only. HTTP v4, JSON v1, Tools v1, iterator and Gmail v4 fields were checked against live Make app metadata. JSON serialization modules preserve quotes, backslashes and multiline text.

In Make's first **Set multiple variables** module, enter `subiect` and `mesaj`. Keep `mod=PREVIZUALIZARE`; leave `numar_asteptat=0` for the first run. Run once manually and inspect the preview count. For the same campaign UUID and unchanged message, enter that count and set `mod=TRIMITE` to send deliberately. A zero/mismatched count or any other mode stops before approval. Use a **new UUID for every new campaign**; preserve its UUID while previewing and sending, so repeated runs cannot silently resend it.

The scenario is created inactive with scheduling `{"type":"on-demand"}`. No periodic schedule or public webhook is used. Verify `isActive=false` after creation. Every claim rechecks the current audience before Gmail; each email has exactly one To address, no CC/BCC. Gmail only receives the server-rendered subject and HTML. A successful Gmail operation is followed by the finish RPC. The database determines audience membership and deduplicates recipients.

Failures use `builtin:Rollback` to stop the scenario with an error. Execution data is confidential; incomplete-execution storage is not presented as enabled because Make readback keeps `dlq:false`. The private SQL campaign ledger retains delivery progress instead. **Never resume directly at Gmail or finish after an uncertain result.** Reconcile delivery and database campaign/recipient state first. A recipient left in `sending` must not be sent again automatically; role and campaign checks must run again before any deliberate recovery. A successful SMTP/API response does not establish inbox delivery.

RPC names and arguments are documented in the builder. `announcement_preview` runs before every send attempt; approval uses the explicit expected count; the iterator consumes opaque recipient IDs; claim returns the sole authorized address and lease; finish confirms that lease after Gmail success. All HTTP requests use TLS and reject redirects.

Make API contracts: `POST /api/v2/scenarios` requires `teamId`, stringified `blueprint`, and stringified `scheduling`. Creation does not activate or run a scenario. `PATCH /api/v2/scenarios/{id}` accepts the generated update body plus the current `baseVersion` to protect concurrent edits. Activation/execution are separate operations. Keychain creation is `POST /api/v2/keys` with `{teamId,name,typeName:"apikeyauth",parameters:{name:"x-spotivity-announcement-key",key:NEW_TOKEN,placement:"header"}}`; the token is never an input to this builder.
